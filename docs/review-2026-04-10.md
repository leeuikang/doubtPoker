## Critical

### ✅ [C-1] `TurnPhase.DISCARD` 미사용 — 게임 흐름 단절 버그

- **위치**: `TurnPhase.java`, `RoundService.java:265`
- **문제**: `DRAW → ACTION → DISCARD` 3단계가 정의되어 있으나 DISCARD 단계로 전환되는 코드가 없어, 클라이언트가 DISCARD 단계를 기대하면 영원히 `INVALID_TURN_PHASE` 발생
- **조치**: `TurnPhase.DISCARD` 제거. 버리기는 ACTION 단계의 마지막 행동으로 처리됨을 주석으로 명시. `TurnPhase.DISCARD`를 사용하던 테스트 2개 삭제

---

### ✅ [C-2] `determineWinners()` + `resolveRound()` 이중 호출

- **위치**: `GameController.java:192-193`
- **문제**: 컨트롤러에서 `determineWinners()`를 단독 호출한 뒤 `resolveRound()`를 호출하는데, `resolveRound()` 내부에서도 `determineWinners()`를 재호출하여 중복 계산 발생
- **조치**: `resolveRound(state, winnerIds)`로 시그니처 변경. 컨트롤러에서 `determineWinners()`를 한 번만 호출 후 그 결과를 `resolveRound`에 전달. `GameControllerTest`, `RoundServiceTest` 내 `ResolveRound` 테스트 전체 수정

---

### ✅ [C-3] GOING_OUT 시 `hasMeldedThisTurn` 플래그 미리셋

- **위치**: `RoundService.java:274-279`
- **문제**: 마지막 카드를 버려 GOING_OUT 발생 시 조기 `return`으로 `advanceTurn()`이 호출되지 않아 `hasMeldedThisTurn`이 리셋되지 않음
- **조치**: `handleDiscard()` 내 GOING_OUT 조기 반환 직전에 `playerState.setHasMeldedThisTurn(false)` 추가. 검증 테스트 추가

---

### ✅ [C-4] `broadcast()` 호출이 `synchronized(room)` 블록 밖 — 레이스 컨디션

- **위치**: `WebSocketEventListener.java`
- **문제**: `synchronized(room)` 블록 안에서 상태를 복원하지만 `broadcast()` 호출은 블록 밖에서 `room.getRoundState()`를 재호출하여 레이스 컨디션 발생 가능. `handleInGameDisconnect`는 반대로 `broadcast()` 2건이 `synchronized(room)` 블록 안에 있어 데드락 잠재 위험
- **조치**:
  - `handleWebSocketConnectListener`: `capturedState = room.getRoundState()`를 블록 안에서 캡처, `state` 중간 변수 제거로 가독성 개선
  - `handleInGameDisconnect`: `broadcast()` 2건을 `synchronized(room)` 블록 밖으로 이동 (`msgToSend` 로컬 변수로 메시지 캡처)
  - 두 메서드 모두 동일한 패턴으로 통일: 상태 변경·캡처는 블록 안, I/O(broadcast)는 블록 밖
- **신규 테스트**: `reconnect_broadcast_uses_state_captured_inside_synchronized_block` 추가

## 2차 리뷰 — Critical

### [R2-C1] `advanceTurn()`이 `lastDoubtableMeldId` 초기화 안 함 — 턴 간 지목 오염

- **위치**: `RoundService.java:advanceTurn()`
- **문제**: `advanceTurn()`은 `hasMeldedThisTurn` 리셋·`turnPhase` 전환은 수행하지만 `lastDoubtableMeldId`를 초기화하지 않는다. 플레이어 A가 멜드를 낸 뒤 정상 턴을 마쳐도 다음 플레이어 B의 턴에서 `lastDoubtableMeldId`가 살아있어 ruleBook §7("자신의 턴에 직전 멜드만 지목") 위반 지목이 가능하다.
- **수정 방법**: `advanceTurn()` 내에 `state.setLastDoubtableMeldId(null)` 추가

---

### [R2-C2] `GameBroadcastService`: `Meld.actualCards`·`isBluff` 마스킹 없음 — 거짓말 정보 노출

- **위치**: `GameBroadcastService.java:maskHandsExcept()` — `masked.setTableMelds(state.getTableMelds())`
- **문제**: `tableMelds`를 원본 참조 그대로 복사하므로 `Meld.actualCards`(실제 카드)와 `isBluff` 필드가 JSON 직렬화 시 모든 클라이언트에 전송된다. S-5에서 손패를 마스킹했으나 멜드 정보 은닉은 누락된 regression이다.
- **수정 방법**: 수신자별 `Meld` 마스킹 로직 추가. 소유자에게는 `actualCards`·`isBluff` 포함, 타 플레이어에게는 `declaredCards`만 포함하는 `MaskedMeld` DTO 또는 직렬화 필터 적용

---

### [R2-C3] `processAction()` 라운드 종료 이중 처리 가능 — 동시성 버그

- **위치**: `GameController.java:processAction()` — 두 `synchronized(room)` 블록 사이
- **문제**: 첫 번째 `synchronized` 해제 후 `updated.getEndCondition() != null` 평가 → 두 번째 `synchronized` 진입 사이에 다른 스레드가 동일 라운드 종료를 재처리할 수 있다. `determineWinners()`·`resolveRound()`·`applyRoundResult()`가 `synchronized` 외부에서 호출되므로 이중 실행 시 점수가 중복 반영된다.
- **수정 방법**: `endCondition` 이후 처리 전체를 단일 `synchronized(room)` 블록 안에서 수행하고, 블록 진입 시 `room.getStatus() == GameStatus.ROUND_END` 가드로 이중 처리 차단

---

### [R2-C4] HMAC 시크릿 하드코딩 — 토큰 위조 가능

- **위치**: `src/main/resources/application.yml:7`
- **문제**: `app.auth.secret: doubt-poker-secret-key-change-in-production` 이 git에 평문 커밋되어 있어 해당 키로 서명된 모든 게스트·CSRF 토큰의 위조가 가능하다.
- **수정 방법**: 환경 변수(`${APP_AUTH_SECRET}`)로 분리. `application.yml`에는 플레이스홀더만 남기고 실제 값은 `.gitignore` 대상 파일 또는 CI 시크릿으로 주입

---

### [R2-C5] CSRF 토큰 만료 없음 — auth 토큰 만료 후 무한 재사용 가능

- **위치**: `GuestTokenService.java:issueCsrfToken()`
- **문제**: CSRF 토큰은 `{guestId}.{HMAC}` 구조로 타임스탬프가 없어 서버 재시작 전까지 영구 유효하다. auth 토큰(1시간 만료) 이후에도 탈취된 CSRF 토큰으로 핸드셰이크 통과가 가능하다.
- **수정 방법**: CSRF 토큰 페이로드에 `issuedAt`·`expiresAt` 추가 및 `verifyCsrfToken()`에서 만료 검증. auth 토큰 만료 시간과 동일하거나 더 짧게 설정

## 2차 리뷰 — Warning

### [R2-W1] `handleDiscard()` GOING_OUT 경로에서 `lastDoubtableMeldId` 미초기화

- **위치**: `RoundService.java:handleDiscard()` GOING_OUT 조기 반환 경로
- **문제**: `hasMeldedThisTurn`은 리셋하지만 `lastDoubtableMeldId`는 남아 있다. `endCondition != null`이면 이후 액션이 차단되므로 실질 게임 영향은 없으나, 브로드캐스트되는 종료 스냅샷에 오염된 값이 포함된다.
- **수정 방법**: 조기 반환 직전 `state.setLastDoubtableMeldId(null)` 추가

---

### [R2-W2] `handleDoubt()` 성공 시 카드 회수 후 파산 체크 없음

- **위치**: `RoundService.java:handleDoubt()` — 지목 성공 경로
- **문제**: 지목 성공 시 멜드 소유자가 `actualCards`를 모두 회수(`addAll`)하여 손패 ≥ 10장이 될 수 있으나, 패널티 드로우(`drawOneFromStock`) 호출 전에 파산 체크가 없다.
- **수정 방법**: `addAll(meld.getActualCards())` 이후 손패 크기를 확인하거나, 파산 체크 로직을 회수 직후에도 실행

---

### [R2-W3] `eliminatedPlayers` 변경이 3곳에 분산 — 캡슐화 필요

- **위치**: `ScoreService.java`, `TournamentService.java`, `WebSocketEventListener.java`
- **문제**: `tournament.getEliminatedPlayers().add()`를 세 곳에서 직접 호출하여 일관성 유지가 어렵다. `eliminatedPlayers`는 `HashSet`으로 `synchronized(room)` 외부 접근 시 동시성 보장이 없다.
- **수정 방법**: `eliminatedPlayers` 변경은 `TournamentService`의 단일 메서드(예: `eliminate(tournament, playerId)`)로 캡슐화

### ✅ [R2-I3] auth/CSRF 토큰 동일 HTTP 응답 반환 — XSS 시 동시 탈취

- **위치**: `GuestAuthController.java`, `GuestTokenResponse.java`, `CsrfTokenResponse.java`
- **문제**: auth 토큰과 CSRF 토큰이 단일 JSON 응답으로 함께 반환되어 XSS 공격 시 두 토큰이 동시에 탈취됨
- **조치**:
  - `GuestTokenResponse` 필드에서 `csrfToken` 제거 (token, guestId, nickname만 반환)

  - `GET /auth/csrf?guestId=...` 엔드포인트 신규 추가 — CSRF 토큰 전용 채널로 분리
  - 클라이언트는 `POST /auth/guest` → `GET /auth/csrf` 2회 호출로 각 토큰 수신
